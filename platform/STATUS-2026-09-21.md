### What the percentages mean

These are explicitly **engineering estimates**, based on current source,
integration failures, and saved QEMU results across the full module set. They are
not mechanically measured completion. They should not be quoted without that
qualification. The ranges reflect incomplete verification, not statistical confidence.

Section 22 of the existing specification enumerates **557 required outcomes in
22 groups**. The repository does not contain a completed machine-executable
outcome-to-code-to-evidence ledger. Therefore there is no defensible exact
numerator such as “418 of 557 fully implemented” or “167 fully qualified.”
Commit counts, package compilation and the number of passing tests do not supply
that numerator. A precise overall percentage remains unavailable.

“Implemented” below means source/runtime machinery exists, not that every
specified outcome works. “Verified” is limited to the actual listed evidence.
Absence of end-to-end evidence is not automatically proof that code is absent,
but it prevents calling that module complete.

### Separate migration tools

signed material, backup conversion, inventory/planning, live synchronization,
cutover/fencing and rollback machinery. Migration console/edge wiring exists.
**No complete original-panel→new-panel rehearsal, final synchronization, cutover,

unsupported-config reporting. Separate migrators do not authorize adding legacy
compatibility to the runtime.

### Cross-cutting platform, API, CLI and UI

Implemented: Go core/gateway/executor separation, Unix-socket protocols, secret
and provider services, signed SPA serving, typed API registry, `panelctl`, durable
repositories and operation journals. Strict UI typecheck/build passed in QEMU.
Installed browser evidence covers login/navigation, selected site/database/mail
workflows and specified desktop/mobile layouts. Many resource screens still need
real forms, complete flows and failure/retry states demonstrated end-to-end.
Earlier generic forms that compiled still failed at runtime; mail and database
were concrete examples corrected during qualification.

### Packages, updates, reboot, Redis/search

Package-maintenance, signed product-update feed/offline-import, reboot admission
and draining, Redis and search lifecycle code exists. Signed node upgrades and a
container-policy reboot were actually exercised. That does not qualify every
package update/reboot/drain/rollback path or Redis/Elasticsearch administration.

### Security, performance and release completion

No comprehensive current-release security, soak, throughput, resource fairness,
capacity, backup RPO/RTO or chaos dossier exists. Specific negative tests passed;
they cannot substantiate a blanket “secure and optimized” certification.
Operator runbooks, unfamiliar-operator rehearsals, final dependency/license
review and outcome-level parity evidence remain required.

The older specification includes CloudLinux/commercial-provider gates and a
support policy that does not match the later ARM64 work. These requirements and
later user decisions need reconciliation before claiming a final support matrix;
they are not silently counted as completed or dropped. The user's later explicit
boundary takes precedence: **normal OLS/LSE/native packages, no custom vendor
forks/builds/patches or product-imposed version pinning**. Existing historical
custom-package evidence and older spec wording are not permission to resume that work.

### Concrete examples of progress versus incomplete integration

- **Mail is no longer just generated config.** A fresh browser-created mailbox
  now authenticates, receives a real message via Postfix→Dovecot LMTP, and returns
  the exact content via IMAP. However, panel webmail still has its separate
  master-credential permission failure, and no external deliverability claim exists.
- **Database is more than CRUD.** Browser SQL/gzip uploads/downloads and isolated
  native imports work for the documented cases. Replacing an existing live
  database safely remains a different, unfinished operation.
- **Sites actually serve content.** Native OLS/PHP/static responses and isolation
  were checked. This does not establish all routing/PHP/cache/edit/deploy/restore
  paths or the equivalent LSE behavior.
- **Installer is real.** Signed bundles have actually installed and upgraded the
  running service stack, including failure/recovery checks. Release sequence66 is
  a checkpoint counter, not66 completed features or66 independent clean installs.
- **Apps have real component installations.** Those establish that selected
  installers work with native dependencies. They do not close the panel's complete
  application-management flow.
- **Fleet/HA/migration/backup remain weakly qualified.** Their considerable source
  volume is not evidence of successful multi-node operation or disaster recovery.
